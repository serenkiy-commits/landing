chrome-capture: вкладка Chrome сразу в AV1

paulirish/chrome-capture в описании GitHub снимает вкладку Chrome: 60–120 fps, до 2160p, видео и звук. README уточняет контейнер: AV1 в .mp4, звук вкладки, без ffmpeg. Демо README открывает на paulirish.github.io/chrome-capture. Команда из README: npx chrome-capture https://paulirish.github.io/chrome-capture/ demo.mp4 4s. README относит запись к Chrome 153 и новее и к методу DevTools Page.startScreenRecording: кадры идут от композитора к кодеру вне процесса, Chrome пишет AV1 в mp4 по ходу и может добавить звук вкладки. Остановка короткая, потому что кодирование уже идёт во время съёмки. Старый путь README описывает у Playwright recordVideo и Puppeteer page.screencast(): JPEG-кадр через CDP, затем сборка ffmpeg. Этот выпуск оба пути не запускал.

startRecording() в README принимает страницу Playwright, страницу Puppeteer или сессию CDP. В примере по умолчанию 60 fps, ширина до 1280 и высота до 720. Звук в комментарии к примеру — стерео Opus 48 кГц, в показанном вызове поле audio выключено. CLI README пишет звук по умолчанию и запускает headless, пока fps не выше 60. На macOS при --fps выше 60 CLI переключается в headful, чтобы Chrome сел на 120 Гц ProMotion. Для @playwright/test README даёт фикстуру screenRecordingFixture: она пишет каждый тест и прикладывает mp4 к отчёту. Таблица замера в README сравнивает один прогон интерфейса длительностью 6,4 с при 1280×800 на M4 Max. У recordVideo полное время 21 с и финализация 3 800 мс, у chrome-capture 11 с и 17 мс. Там же трафик WebSocket 10,5 МБ и 450 КБ, файл 480 КБ и 330 КБ, PSNR 32 дБ и 34 дБ. Регулятора битрейта и CRF README нет. Кодирование README описывает как libaom AV1, realtime, один проход, VBR, и приводит шкалу: 2 Мбит/с на 720p30, 9 Мбит/с на 1080p60, 18 Мбит/с на 1080p120, 72 Мбит/с на 2160p120. Пометка README от 10 ноября указывает открытый PR Playwright про Page.startScreenRecording. Статус этого PR выпуск не проверял. Экспериментальный page.record() README относит к Puppeteer v25.10 и новее.

Кому: тем, кто снимает вкладку Chrome в mp4 для демо или теста и хочет файл AV1 из композитора. deepseek-ai/chat-demo в описании GitHub назван коротко: Chat Demo. README длиннее: статичный чат на API DeepSeek. Своего бэкенда приложения нет, браузер ходит напрямую в настроенный сервис. Онлайн-демо README открывает на deepseek-ai.github.io/chat-demo. Сборка pnpm build пишет статику в dist/.

Ключ и настройки README кладёт в localStorage. Переписки и исходные вложения — в IndexedDB. Данные изолированы профилем браузера и origin сайта. Отправка сообщений, загрузка вложений и речевые функции передают соответствующее содержимое в настроенный API. Список возможностей README: несколько диалогов с автозаголовком, правка запроса, повтор ответа и ветки сообщений; поток ответа, режим размышления, поиск, чтение ссылок и ссылки на источники; вложения файлом, вставкой или перетаскиванием; голосовой ввод и чтение ответа вслух; Markdown, подсветка кода, формулы KaTeX и схемы Mermaid; упрощённый китайский и английский, светлая и тёмная тема, мобильная вёрстка, импорт и экспорт истории в ZIP. Импорт после подтверждения заменяет все локальные диалоги и вложения. Экспорт забирает диалоги и локально доступные исходные картинки и не включает ключ, настройки и исходные вложения не-картинки. Удаление всех чатов в настройках сохраняет ключ и настройки и не удаляет файлы, уже отправленные в API. В rspack.config.ts README указывает origin по умолчанию https://api.deepseek.com. Чат по умолчанию идёт в модель deepseek-flash через Messages и Files API, совместимые с Anthropic. Речь ходит в конечные точки ASR и TTS. Запросы несут расширения для поиска, чтения ссылок, заголовков и latest_reminder, поэтому сервис должен эти возможности поддерживать. Форматы вложений README отдаёт на проверку серверу.
