nestjs/agent-skills: скиллы NestJS для агента

nestjs/agent-skills в описании GitHub — agent skills для фреймворка Nest (Node.js). README называет это официальными Agent Skills для сборки и расширения приложений NestJS. Скилл, по README, даёт агенту то, чего нет в обучающих данных: текущие API, которые часто новее модели; пакеты Nest первой стороны; ошибки, которые всё ещё проходят тесты. В README перечислены примеры таких ошибок: вход, который выдаёт, какие адреса почты существуют; @IsOptional(), пропускающий null до ответа 500; ограничитель частоты, который не видит пользователя; поток событий, который живёт дольше отозванного ключа. Каждый скилл — папка с SKILL.md и каталогом references/. README пишет, что каждый рецепт прогнан на выпущенных пакетах. Скиллы читает любой агент формата Agent Skills: Claude Code, Codex, Cursor и другие. Агент подхватывает скилл, когда описание совпадает с задачей, отдельной команды вызова нет.

В таблице README шесть скиллов. nestjs — новое или расширяемое приложение: старт проекта, раскладка, модули, где лежат документы, частые ошибки. nestjs-feature — эндпоинты: куда класть код, модули и провайдеры, проверка тела через Zod с @Body({ schema }) или class-validator, коды статуса, ошибки, параметры HTTP, Server-Sent Events. nestjs-auth — @nestjs/authentication (пароли, сессии, токены, ключи API) и @nestjs/authorization (политики). nestjs-data — @nestjs/drizzle и @nestjs/typeorm, миграции, безопасные обновления, постраничная выдача, транзакции. nestjs-testing — модульные, сервисные и сквозные тесты, подмена провайдеров и глобальных гардов, вход тестового пользователя. nestjs-production — конфигурация, журналы, наблюдаемость через NestJS Observe, проверки здоровья, ограничение частоты, OpenAPI, остановка, выкладка.

coordinator: одна сессия ведёт флот в Herdr

petekp/coordinator в описании GitHub превращает одну сессию Claude Code в координатора, который запускает, наблюдает и убирает флот сессий агентов в Herdr. README уточняет устройство. Человек задаёт область — репозиторий или часть продукта — и шлёт запросы по мере появления. Координатор пишет бриф на задачу и поднимает отдельную сессию агента: свой Git worktree и своя вкладка. Он смотрит эти сессии, передаёт их вопросы человеку, проверяет работу и убирает задачу, когда она села. Человек говорит с одной сессией, параллельно работают до трёх других. Это пара скиллов для Claude Code и скрипты на Python, которые управляют Herdr. Herdr держит каждого агента в терминале, который остаётся живым, и показывает их в одном приложении.

Координатор стартует командой /coordinator <область или проект> и ведёт одну область. Состояние лежит в Markdown-файле backlog: что входит в область, что человек утвердил, что открыто и что сделано. Backlog переживает перезапуск. Делегат — сессия на одну задачу: worktree, бриф с критерием готовности и местом остановки, вкладка в Herdr под координатором. Остановившись, делегат пишет REPORT.md. Наблюдатель fleet_watch.py работает в фоне и будит координатора, когда делегат закончил, спросил или застрял, а также когда pull request влит, провалил проверки или получил ревью. Ограничение числа не пускает больше трёх делегатов сразу. Тихий делегат, который сутки не отвечает, завершают и позже возобновляют той же сессией, если для него что-то пришло. Второй скилл, fleet-sweep, снимает законченные worktree, ветки, вкладки и осиротевшие процессы. То, что потеряло бы работу, он не трогает и спрашивает человека. Мелкие обратимые решения координатор принимает сам и говорит, что выбрал. Спрашивает, когда ответ меняет, что будут строить, стоит времени или денег, касается других людей или является вопросом вкуса. Вопросы приходят пачками не больше пяти, у каждого варианты и рекомендация.

Кому: тому, кто уже работает в Claude Code и хочет одну сессию-распорядителя над несколькими делегатами в Herdr. Как поставить по README. Нужны herdr-core (hc), приложение Herdr, Claude Code, Python 3.9 или новее, git и вошедший в аккаунт gh — статус pull request для областей с репозиторием на GitHub. Скрипты используют только стандартную библиотеку Python. README пишет, что связку проверяли на macOS с herdr-core 0.1.21, приложением Herdr 0.1.15 и Claude Code 2.1.325. herdr-core ставится скриптом curl -fsSL https://releases.herdr.dev/core/install.sh | sh, приложение качают с herdr.dev. Агенту можно отдать фразу из README со ссылкой на SETUP.md: он ставит Herdr, скиллы и плагин Inbox и предлагает Vignette и боковую панель Herdr, спрашивая перед каждым шагом. Вручную: клон в ~/src/coordinator и install.sh. Скрипт вешает оба скилла ссылками в ~/.claude/skills и ~/.agents/skills. Клон README просит не переносить: ссылки смотрят внутрь него. Обновление — git pull в клоне. При первом пробуждении за сутки наблюдатель проверяет, отстал ли клон от upstream, и координатор сообщает об этом. Сам он не подтягивает изменения. Снятие — install.sh --remove, затем удаление клона. Необязательный мод inbox собирает вопросы в одну панель; скрипты читают сохранённые вопросы, если он стоит. В каталоге herdr/ лежит необязательная раскладка Herdr: закреплённые координаторы сверху, делегаты под ними. Она есть в галерее раскладок по адресу herdr.dev/layouts/petekp/coordinator--herdr. Раз в сутки верхняя строка боковой панели проверяет GitHub на новую версию раскладки и показывает точку, если версия есть. Нажатие даёт строку для агента.

Первый запуск по README: открыть приложение Herdr и вкладку терминала, запустить Claude Code в нужном репозитории, выполнить /coordinator <область>. Координатор спрашивает, что входит в область, создаёт backlog и докладывает, что нашёл. Запрос крупнее нескольких файлов уходит делегату в новую вкладку, человеку сообщают имя вкладки. Вопрос «where are we» печатает таблицу делегатов, pull request и открытых вопросов. Настройки по умолчанию есть у каждого ключа. Свой файл — копия config.example.json в ~/.config/coordinator/config.json; значения в примере README называет примерами, не значениями по умолчанию. Среди ключей: каталог backlog (по умолчанию ~/.config/coordinator/backlogs), каталог состояния, список областей, чьих делегатов не завершают за тишину, дополнительные аргументы Claude Code для каждого делегата, предел backlog вне секции Done — 40 КБ, около 10 000 токенов. Ограничения README пишет прямо. Вкладки делегатов живут в приложении Herdr, без него схема не работает. Снятие worktree переносит игнорируемые файлы, в том числе .env и .scratch/, в <основная копия>/.scratch/parked/. Эти папки скрипт не удаляет. Делегаты идут в том режиме разрешений Claude Code, который стоит у человека: в режиме по умолчанию каждый останавливается на запросе разрешения и на доверии к папке в новом worktree, пока человек не ответит во вкладке. Если входная оболочка — fish или другая не-POSIX, делегат стартует через /bin/sh и ищет hc, claude и python3 в её PATH. Лицензия MIT. Язык по снимку API — Python. chronytop: TUI для chrony

geerlingguy/chronytop в описании GitHub — TUI для наблюдения за сервером времени chrony. README ставит его в ряд с btop. Программа рисует график запросов NTP в секунду и показывает счётчики сервера, клиентов, которых chrony ограничивает по частоте сильнее всего, источники, tracking, канал, загрузку CPU и память, в том числе самого chronyd. Панели меняют размер вместе с терминалом, их можно показать и спрятать. Требования README: Linux и chronyd 4.3 или новее. Более старые версии, по README, могут работать, их не проверяли. Для панелей сервера и клиентов под ограничением нужны root или sudo, отдельный раздел README описывает запуск без root. Это один статический бинарник. Зависимостей вне стандартной библиотеки Go нет, поэтому README пишет, что он идёт на Debian, Ubuntu, Fedora, RHEL, Arch, Alpine и других дистрибутивах. С chronyd программа говорит напрямую по его Unix-сокету команд или по UDP с флагом -host. chronyc не нужен.

Кому: тому, кто держит chronyd на Linux и хочет смотреть его в терминале, а не разбирать вывод chronyc. Как поставить по README. Бинарник под свою архитектуру — из релизов, затем sudo install --owner=root --group=root --mode=755 chronytop-linux-amd64 /usr/local/bin/chronytop. Сборка из исходников — Go 1.24 или новее, CGO_ENABLED=0 go build -trimpath -ldflags "-s -w" -o chronytop .. Путь сокета по умолчанию сборщик может подменить флагом -X main.defaultSocket=.... Запуск — sudo chronytop. Флаги README: -i интервал опроса, по умолчанию 1 с, допустимо от 500 мс до 10 с; -p минимум пакетов, чтобы клиент попал в список ограничиваемых, по умолчанию 100; -socket путь сокета, по умолчанию /var/run/chrony/chronyd.sock; -host наблюдение по UDP, адрес, host:port или [IPv6]:port, порт по умолчанию 323; -version печатает версию и выходит. Клавиши: 1–7 показывают и прячут панель, + и - меняют частоту опроса, ? и h — справку, Esc закрывает справку или выходит, q выходит. Видимые панели и интервал пишутся при выходе в ~/.config/chronytop/chronytop.conf (у root — в /root/.config/...) и читаются при следующем запуске. -i перекрывает сохранённый интервал. Список ограничиваемых клиентов обновляется в фоне каждые 10 секунд. Фильтр -p применяет сам chronyd, поэтому README пишет, что список дёшев даже на публичном сервере с сотнями тысяч клиентов.

Удалённый хост: chronytop -host ntp.example.com. Сервер должен разрешить это в chrony.conf: bindcmdaddress, cmdallow и opencommands со списком команд, куда README добавляет serverstats и clients. opencommands есть в chrony 4.7 и новее и заменяет набор по умолчанию, поэтому список в README сначала повторяет штатные команды. Панели сети и системы для удалённого хоста не показываются. Без root, если сокет недоступен, программа уходит на UDP localhost, как chronyc. Тогда видны все панели, кроме сервера и ограничиваемых клиентов: serverstats и clients по UDP chronyd отдаёт только если это разрешено. На chrony 4.7+ README просит добавить ту же строку opencommands, перезапустить chronyd и запускать chronytop любым пользователем. Без cmdallow эти запросы принимает только localhost. На более старых версиях README предлагает добавить пользователя в группу chrony, и только если группа может писать в /run/chrony: программа создаёт там сокет ответа. На Debian и Ubuntu этот каталог группе не открыт, там README оставляет sudo. Где группа работает, её члены получают полный доступ к сокету управления chronyd и могут сдвинуть часы или сменить источники. Раздел безопасности README: программа шлёт chronyd только команды наблюдения на чтение, не сбрасывает счётчики и не запускает другие программы; локальную статистику читает из /proc; UDP использует с -host или как запасной путь на localhost; сокет ответа создаёт в отдельном каталоге со случайным именем рядом с сокетом chronyd и удаляет при выходе; файл настроек пишет только если настройка изменилась, пропускает файл и каталоги, если владелец не тот пользователь, который запустил программу, и пишет через временный файл, не следуя по symlink. Непечатные символы из данных chrony она вырезает, чтобы в терминал не попали управляющие последовательности. CI на каждое изменение гоняет go vet, staticcheck, gosec и govulncheck и проверяет программу на chronyd 4.3, 4.6 и последнем релизе. Лицензия MIT. Язык по снимку API — Go. Тем в снимке нет. Python 3.10 или новее, PyTorch 2.2 или новее. pip install git+https://github.com/kobimusic/dettato, затем dettato song.mp3 -o out/ пишет out/song.mid и out/song.json. Как это устроено по README. Транскрайбер — сеть дорожек, равноправная по высоте. Она читает гармоническую лог-частотную спектрограмму и выдаёт вероятности onset, frame и offset для каждой из 88 клавиш, по два голоса на клавишу, шаг 20 мс. Песня идёт перекрывающимися окнами по 8 с, окно каждые 2 с, среднее с окном Ханна, ноты берутся поиском пиков. Сеть прогоняется по записи один раз, этот проход кормит починку и группировщик. Сначала оценивается строй, и если он явно ушёл от A440, проход идёт по перестроенному звуку. Модель починки — трансформер уровня ноты: нота плюс свидетельства транскрайбера (карты вероятности вокруг ноты и его последнее скрытое состояние). Она решает, какие ноты оставить, где у них начало и конец и каких нот не хватает. Группировщик собирает внутренние признаки транскрайбера на каждой починенной ноте и даёт ноте инструмент и вектор дорожки. Ноты кластеризуются. Дорожка остаётся, только если она явно свой инструмент, одинаковые инструменты сливаются. Барабаны — две маленькие модели, набор ударных и оркестровая перкуссия. Маршрутизатор слушает всю запись и выбирает одну. Модели барабанов нужен звук от 40 кГц, на более низкой частоте дискретизации ступень пропускается. Пределы README: высоты — 88 клавиш фортепиано, не больше двух нот на одной клавише сразу; имена инструментов приблизительные, на живом джазе около четверти нот саксофона или соло-гитары может уйти в дорожку фортепиано, насыщенная синтезаторами музыка именуется менее надёжно, духовой оркестр получает грубые имена; барабанов нет у источников ниже 40 кГц.
